# Compressing LLM Documentation: Foundations & Non-Trivial Patterns

> Reference dossier for building a `compress-llm-documentation` skill. Densely structured, with opinionated recommendations.

---

## 1. Core Mental Model: What "Compression" Means for LLMs

LLMs read **tokens**, not characters. They parse **structure**, not visuals. They **infer** what you omitted if you signal it well. So LLM-doc compression is not "shrink prose" — it is **token-density engineering** + **inference amplification**.

**Three sources of compression:**

| Source | Mechanism | Example |
|---|---|---|
| **Lexical** | shorter tokens, shared vocabulary | `must` → `M`, `DON'T` → `!` |
| **Structural** | tables, schemas, decision trees | prose ❌ / table ✅ |
| **Referential** | implicit knowledge, pointers, deltas | `@auth-jwt-v2` instead of paragraph |

**Key insight:** most doc bloat is **restating the obvious** or **restating elsewhere**. Strip both, link to the rest.

---

## 2. LLM Reading Mechanics — Why Human-Optimized Docs Are Wasteful

| Human doc | LLM doc | Why |
|---|---|---|
| Headings for scanability | Headings as **semantic boundaries** | LLMs parse hierarchy as semantic structure, not as visual ramp |
| Sentences for rhythm | Sentences as **truth carriers** | Each sentence is a fresh claim; long sentences dilute |
| Examples after theory | Examples as **first-class spec** | Few-shot > instructions for LLMs |
| Visual emphasis | `code` / `key:` as **anchors** | Bolding/italic are noise; backticks are parseable tokens |
| Whitespace for legibility | Whitespace ≈ free, but not always | LLMs tolerate dense text, but **section breaks matter** |

**Rule:** LLMs have **no graphics, no mouse, no progressive disclosure**. Write as if a blind, fast, knowledgeable reader needs every byte to count. Anthropic (2024–2025) calls this *context engineering*: https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview

**Also known:** *context rot* — beyond a token budget, recall quality degrades non-linearly. Prioritize what hits the **early + late** positions of the prompt (U-shape bias). See https://arxiv.org/abs/2307.03172 (Lost in the Middle, Liu et al.).

## 3. Compression Techniques — Taxonomy

### 3.1 Lexical / Vocabulary Compression

- **Stable shorthand dictionary** defined once per doc, reused.
  ```
  M = must | S = should | X = forbidden | ? = optional
  R = read | W = write | D = delete | U = user | A = admin
  ```
- **ISO-style brevity** — verb tokens: `parse`, `emit`, `assert`, `reject`, `delegate`, `spawn`.
- **Telegraphic style for instructions**: drop articles, drop `that`, drop `the` when scope is local.
  - ❌ "The agent must ensure that the response does not contain…"
  - ✅ "A: response must not contain…"

### 3.2 Structural Compression

- **Tables over prose** for ≥ 3 attributes of the same kind.
- **Decision trees** for branching flows (cuts nested conditionals by 60–80%).
- **Schema/YAML frontmatter** for agent self-description: a 30-line YAML block replaces 5 paragraphs.
- **EBNF / BNF grammars** for input/output formats — 5 lines of grammar vs 30 lines of "what is allowed".
- **JSON Schema for contracts** — `required`, `enum`, `pattern` collapse "list of allowed values" sections.
- **Regex as spec** — for path/format rules, one line replaces a paragraph.

### 3.3 Referential Compression

- **`@import` / pointer syntax** — references to other parts of the codebase or doc set.
- **Delta-from-default** — only describe departures from base behavior. If every agent has `git_status`, don't repeat; only mention overrides.
- **Negative specification** — "forbidden: …" lists are denser than "allowed: …" when the allow-list is long.
- **Inheritance & composition** — name shared components once, reference by id.

### 3.4 Semantic Compression (LLM-Only)

- **Few-shot exemplars** — 1–3 I/O pairs encode more rules than 10 lines of prose.
- **Counter-examples** for nuance — show the wrong output once, the model locks on.
- **Implicit assumptions** — if "you know git", don't re-explain commits.
- **Stacked delimiters** — `###` then `---` then a labelled block: gives LLMs unambiguous section boundaries.

## 4. Non-Trivial & "Hacky" Techniques

These are the bits practitioners don't put in style guides but they work.

### 4.1 Position Bias Exploitation

LLMs over-weight prompt **head** and **tail**. Place:
- **Mission-critical rules** at top (`# HARD RULES`) and bottom (`# HARD RULES (repeat)`).
- **Reference material** in the middle (rarely needed, can drift).

This is *recency+primacy exploitation*, more effective than any organizational tip.

### 4.2 KV-Cache-Friendly Formatting

Cached tokens must match **byte-for-byte** across calls. Stable formatting = cache hits = 10× cost drop on long docs.
- Use fixed indentation.
- Avoid variable-length enumerations, time stamps, random IDs in stable docs.
- Don't auto-generate dates/IDs into skill files unless needed.

### 4.3 Symbolic Logic for Specs

Replace English disjunction with operators:

```
∀ req (req.op ∈ {create,delete} → auth.role == "admin")
∃ user (user.subscribed == true ∧ user.tier ∈ {gold,platinum})
```

A `∃ / ∀ / → / ∧ / ∨` spec is ~10× denser than English equivalent, and unambiguous.

### 4.4 Pseudo-Code as Compression

Pseudo-code is dense, parseable, and language-agnostic:

```
on_input(msg):
  parsed = parse(msg)
  if not validate(parsed): return Err(E_PARSE)
  ctx = lookup(parsed.id) or default_ctx
  out = invoke(parsed.tool, ctx)
  log(out, parsed, ctx)
  return out
```

~150 tokens vs ~600 for "When the agent receives an input message, it should first attempt to parse the message…"

### 4.5 Set / Tuple Notation for Lists

- ❌ "Allowed file extensions are .py, .ts, .go, .rs, .java, .kt, .swift, .c, .cpp, .cs, .rb, .php, .scala, .m, .mm."
- ✅ `exts: py|ts|go|rs|java|kt|swift|c|cpp|cs|rb|php|scala|m|mm`

### 4.6 Image-Reference Compression

Large diagrams in SVG/PNG can be 5–50 KB but worth 1000 tokens of doc when re-loaded each call. Encode diagrams as **referenced URLs** + a tiny caption — load only when needed, cache once.

### 4.7 Formula Compactness

Mathematical spec for behavior can compress entire sections. Example — a routing policy:

```
score(p) = α·relevance(p, q) + β·recency(p) − γ·spam(p)
choose = argmax_{p∈P} score(p)
```

### 4.8 Binary / Enum Signaling

LLMs latch onto enum tokens:
- `type: A|B|C|D` instead of "The agent supports four modes: A is for X, B is for Y…"
- One token per state.

### 4.9 "Negative Anchors" — Explicit Anti-Patterns

```
✗ NEVER: echo user input verbatim
✗ NEVER: split a single task across > 3 tool calls if 1 suffices
```

Outperforms "Always be concise" because LLMs pattern-match on the **form** of the instruction, not the intent.

### 4.10 Idiomatic Multi-Language Notes

For multilingual docs, prefer **scripts over transliteration** — `Σ = {…}` instead of "the sum of…". Predictable across languages.

### 4.11 Hashed/Id-Only References

Refer to code/files by hash or short id:
- `@auth/jwt.verify@v2`
- `module:acs.svc.billing#v3`

This is Git/Cargo-style. Information-dense, version-stable.

## 5. Format-Specific Patterns

### 5.1 `agents.md` / `CLAUDE.md` / `.cursorrules`

**Canonical shape (low-token, high-effect):**

```markdown
# Role
[2–5 sentences max]

# Hard Rules
- M: <rule>
- X: <forbidden>

# Tools
- fs.{read,write,edit}   # sandbox = /repo
- shell.exec             # whitelist = npm,go,git,make
- web.fetch              # timeout = 8s

# Conventions
- commits: conventional
- lang: en
- tests: required for any *.ts in /src

# Workflow
[decision tree or numbered steps]
```

Total: **200–600 tokens** for a fully specified agent. Compare typical 3000-token `agents.md`.

### 5.2 Skill Files (Anthropic Skills Spec, 2025)

Format observed at https://docs.anthropic.com/en/docs/agents-and-tools/agent-skills/overview

- **YAML frontmatter** with `name`, `description`, `trigger`.
- **Body** is *instructions*, not data — body lives in the system prompt, not in user context.
- Skills **compose by reference**, not by content copy.
- Embed tokens in frontmatter description: a good `description` enables trigger; bad one wastes tokens forever.

### 5.3 Memory Files

Two-tier pattern:
- **Always-on memory** (≤ 1 KB, semantic-stable) — user prefs, env, hard rules.
- **Recallable memory** (refs/index) — point to long-form logs by ID.

Never inline large memory into always-on. Inline only the **deltas**.

### 5.4 PR / Changelog / API Docs

- Use `diff`-style fragments for changes, not "Before v2.3, this did X; now it does Y."
- API: terse OpenAPI/JSON-Schema dump + 1 example per endpoint. LLMs fill gaps.

## 6. How To Compress — Pipeline

Suggested **staged pipeline** for the skill:

```
1. INPUT        → read source markdown
2. LEXICAL      → replace verbose phrases with stable shorthand
                  (replacement table from skill config)
3. STRUCTURAL   → tables, decision trees, grammars
                  for repetitive prose blocks
4. DELTA-AWARE  → diff vs known baseline (e.g. default agent spec)
5. REFERENTIAL  → replace duplicated content with @links
6. SEMANTIC     → prune — keep rules, drop rationale/restatements
                  keep headings, drop sub-bullets that just restate
7. POSITION     → ensure HARD RULES live at head + tail
8. STABLE-OUT   → byte-stable formatting for KV-cache friendliness
9. VALIDATE     → token count < budget, no orphan refs,
                  no implied must-rules from prose
```

**Token budget rule of thumb:**
- Agent instructions: ≤ 2 K tokens.
- Per-skill body: ≤ 4 K tokens.
- Total tool/skills context: ≤ 20 K tokens (rough — test empirically per model).

## 7. What to DELETE (Most Common Bloat)

1. **Apologies / caveats / hedging** ("Please note that…", "It's worth mentioning that…") — pure loss.
2. **Restatements of preceding points** with different words.
3. **Empty sections** ("Future work", "Limitations" — empty or one-line).
4. **Restated UI / styling guidance** (e.g. "Use code blocks for code").
5. **First-person pedagogy** ("Let me explain…", "Think of it like…").
6. **Lore / origin / motivation**. Belongs in commit messages, not skills.
7. **Definitions of common terms** the model already knows (HTTP, JSON, regex, Git, RAG, etc.).
8. **Version history / changelog in primary docs** (move to CHANGELOG.md).
9. **Conclusion / summary paragraphs**. The summary is the doc itself.
10. **Duplicate examples.** Two examples is a redundancy proof; one example is enough.

## 8. Non-Obvious Edge Cases

| Edge case | Recommendation |
|---|---|
| Long docs as one file | Split — but use a `## INDEX` file that names each chunk. LLM pulls what it needs. |
| Cross-doc naming drift | Pin a glossary at top of every doc; reuse the same tokens for the same concept everywhere. |
| Examples growing stale | Use **template placeholders** (`{{user_query}}`, `{{tool_call}}`) — examples generalize. |
| Mixing human+LLM audiences | Two deliverables: a long human doc + a derived LLM-only `.llm.md`. Don't compromise for both. |
| Multi-model portability | Avoid model-specific tokens (e.g. `<antmlthinking>`). Stay close to plain markdown. |
| Compression that breaks meaning | A 50% smaller doc with 5% ambiguity is **worse** than a 20% smaller doc with 0% ambiguity. **Never** compress more than the LLM can plausibly recover. |

## 9. Skill Workflow — Suggested Prompt Skeleton

```
## compress-llm-documentation

INPUT  : markdown text, optional {role, budget_tokens, baseline}
OUTPUT : compressed markdown, with audit trail of removed/merged/linked spans

STEPS:
1. classify doc type: agent-spec | skill | memory | api | tutorial
2. detect sections and tag each: hard-rule | soft-rule | example | narrative | meta
3. for each tag apply type-specific rules:
   - hard-rule     → keep verbatim, hoist to head/tail
   - soft-rule     → tersify, group in tables
   - example       → keep ≤ 3, deduplicate
   - narrative     → delete unless novel info
   - meta          → delete or move to frontmatter
4. extract & dedupe anchors (terms, tools, paths)
5. ensure stable formatting for KV-cache
6. token count; if > budget, recurse on lowest-value sections first
7. emit diff summary so a human reviewer can audit

CONTRACT:
- preserve every imperative (must/never/always)
- never alter semantic meaning of hard rules
- emit removed spans grouped by tag (for audit)
- provide byte-stable output if `stable=true`
```

## 11. Author's Opinion (cut if unhelpful)

- **Most "skills" fail not because the model can't do it, but because the skill didn't get out of the model's way.** Compression is half cognitive — half removing the trust-killing hedging and meta-paragraphs.
- **The single highest-leverage trick:** define a 20-token **stable shorthand legend** at the top of every LLM doc. Reusing `M`, `X`, `→`, `:`, `kind=k` consistently across all your docs compresses each subsequent doc another 10–20% via shared context the model already absorbed.
- **Don't trust LLMLingua for skills.** It optimizes for **any** task; it doesn't know that **hard rules are precious** and prose is compressible. Hand-curated compression with a `hard-rule` preserve-list is more reliable.
- **The most underused structure for skills: tables.** A well-cut table replaces 4–10× its weight in prose. Anyone writing skills should learn table discipline.
- **Compression is a habit, not a one-shot tool.** The skill should expose **subcommands**: `tersify`, `dedupe`, `split`, `shorthand-add`, `audit-removals`. Don't bundle them.
- **Watermark every removed span.** Compressed output without an audit trail is a black box; auditors will reject it. Always emit a sidecar `.removed.md`.
